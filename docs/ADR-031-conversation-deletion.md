# ADR-031：对话删除与 SQLite 空间回收

日期：2026-10-27。范围：用户要求删除过多对话以减少存储；实际验证与运行结果见 PLAN W-069。

## 用户操作与保留范围

会话列表中每项提供独立删除按钮；确认说明会话与历史不可从应用恢复，正在处理的回复将停止，已保存的档案、计划、求职资料和偏好继续保留。取消确认不发请求；删除当前对话回到新对话，删除其他对话保持当前消息与未发送草稿。用户未点删除的真实对话不自动清理。

DELETE /api/v1/workflows/conversations/{conversation_id} 使用 ConfirmInput 与 If-Match。服务端校验工作区归属、对话版本及所有关联运行的所有者；版本过期需刷新重试，不默认删除新出现的消息。成功返回 204，重复读取消息、恢复、重试与 SSE 均不能访问已删除对话。

## 清理顺序

1. 在既有 owner 锁内取消相关运行，立即硬删除会话/摘要、消息、模型决策/工具/领域回执、事件、这些记录的全部修订与审计副本。
2. 只保存 ID 的 conversation_cleanup 队列，不保存标题、聊天或结果正文。正在运行的任务元数据暂留，使晚到的模型响应和 Worker 能识别取消并安全退出。
3. 单 Worker 在处理器之间清理队列：清除对应 LangGraph checkpoints/writes，再删除任务、状态/Outbox/Inbox、任务幂等记录和单任务配额桶。成功后清空队列清单与修订，只留下小型压缩重试标记。
4. 对当前 SQLite 业务库和检查点库执行 WAL checkpoint、VACUUM 与截断，以实际回收磁盘空间。数据库忙时保留队列，后续周期重试；不停止 Worker 或将删除正文重新写回。压缩成功后移除重试标记。

队列采用稳定 ID；清理完成前，原创建幂等键不能重新创建同 ID 对话，避免误清新记录。原生幂等回执和删除后的 404 继续阻止旧页面恢复已删除消息。按现有单 Worker 部署执行，不从 API 线程直接清理仍可能被写入的检查点。

## 数据与额度

无正文的模型用量和日/累计预算继续保留，删除对话不退还已消费额度；原预算上限不变。对话工具已经提交的独立业务事实、计划、简历、申请、证据和显式偏好不随对话级联删除，仍使用各自的修改/撤回/删除入口。既有业务备份沿用原保留规则。

沿用 GrowthRecord、GrowthRevision 与原任务/事件表，不修改数据库 Schema，不新建存储卷，不把删除改成长期软隐藏。清理包含历史旧任务回执和当前有界模型/工具回执；未来增加回执格式或调用上限时，应同步扩展关联清理与回归。
